# M-PIN v2.0

## Profile 01 — AI

**Status:** FROZEN **Version:** 2.0 **Document Type:** Normative Profile
Specification **Requires:** M-PIN v2.0 Core 01–12

------------------------------------------------------------------------

# 1. Purpose

This Profile applies the M-PIN v2.0 Core architecture to AI services.

It defines how an AI service participates as a Friend while preserving:

- Owner-controlled persistent state;
- Friend Folder isolation;
- AI service autonomy;
- native AI Runtime and UX;
- bounded synchronization;
- Owner-controlled persistence;
- separation between M-PIN state and AI-provider internal state;
- separation between M-PIN access and secondary data use;
- portability of Owner continuity.

This Profile does not create a separate AI-specific M-PIN architecture.

AI is one application of the same M-PIN Core used by other Friend
categories.

------------------------------------------------------------------------

# 2. Profile Thesis

The canonical AI rule is:

> **An AI is a Friend. It may use its Owner-authorized Friend Folder
> during a valid Session, but it does not become the Owner of the
> Owner’s M-PIN continuity.**

Conceptually:

Owner │ ▼ M-PIN │ ▼ AI Friend Folder │ ▼ AI Friend │ ▼ AI Runtime │ ▼
Native AI UX

The AI remains an independent service.

M-PIN remains the Owner-controlled persistence boundary.

------------------------------------------------------------------------

# 3. AI as Friend

For this Profile, an **AI Friend** is an AI service participating in
M-PIN under the Friend role defined by Core.

Examples may include:

- conversational AI;
- AI assistant;
- multimodal AI;
- coding assistant;
- research assistant;
- AI agent service;
- AI embedded in another compatible service.

The Profile does not depend on one AI vendor, model family, or
interface.

------------------------------------------------------------------------

# 4. AI Is Not M-PIN

The AI Friend MUST remain distinct from M-PIN.

The AI may:

- reason;
- generate;
- search;
- plan;
- use tools;
- maintain Runtime context;
- present its own UX.

M-PIN does not perform those AI functions merely because it stores the
AI Friend’s Owner-controlled persistent state.

------------------------------------------------------------------------

# 5. AI Is Not Owner

An AI Friend MUST NOT become the architectural Owner of M-PIN merely
because:

- the Owner uses it frequently;
- it creates most of the content;
- it interprets the payload;
- it provides memory features;
- it hosts the user interface.

The Owner remains the authority over M-PIN persistence.

------------------------------------------------------------------------

# 6. One AI, One Friend Folder

Each distinct AI Friend has its own Friend Folder relationship.

Canonical model:

M-PIN ├── AI Friend A Folder ├── AI Friend B Folder └── AI Friend C
Folder

Therefore:

AI Friend A → Folder A

does not imply:

AI Friend A → Folder B AI Friend A → Folder C

------------------------------------------------------------------------

# 7. No Shared AI Memory Pool

M-PIN v2 does not define one universal memory pool automatically visible
to every AI.

The following model is prohibited by default:

M-PIN ↓ shared memory ↓ AI A + AI B + AI C

Instead:

M-PIN ├── Folder A → AI A ├── Folder B → AI B └── Folder C → AI C

Common Owner ownership does not mean common Friend visibility.

------------------------------------------------------------------------

# 8. AI Friend Folder

The AI Friend Folder is the Owner-owned persistent M-PIN area associated
with one AI Friend.

It may contain Friend-defined persistent data required to restore or
continue the Owner’s state with that AI Friend.

Examples may include:

- conversation lists;
- conversation content;
- Owner-created persistent context;
- Friend-specific memories;
- preferences;
- settings;
- environment/configuration state;
- other AI-service-specific persistent state.

These examples are non-exhaustive and non-universal.

------------------------------------------------------------------------

# 9. AI Payload Semantics

The AI Friend determines the meaning and service-specific structure of
its own payload.

M-PIN does not need to understand whether a payload object represents:

- a conversation;
- memory;
- preference;
- project;
- tool configuration;
- another AI-specific object.

M-PIN preserves the structural, identity, integrity, authorization, and
persistence boundary around that payload.

------------------------------------------------------------------------

# 10. Decision 120 in the AI Profile

The responsibility boundary is:

AI Friend: - defines AI payload semantics; - defines AI-specific payload
composition; - interprets its saved data; - manages semantic schema
evolution.

M-PIN: - preserves Friend identity and Folder binding; - provides
minimum boundary metadata; - enforces authorization and isolation; -
protects integrity; - governs M-PIN persistence.

The exact universal AI payload schema is not defined by M-PIN v2.0.

------------------------------------------------------------------------

# 11. First Synchronization

When an AI Friend synchronizes with an M-PIN for the first time:

Owner ↓ initiates Sync through AI Friend ↓ Owner identifies/opens
applicable M-PIN ↓ Owner authority established ↓ AI Friend Identity
verified ↓ M-PIN resolves AI Friend Folder ↓ Folder absent ↓ Owner
approval requested ↓ AI Friend Folder created and bound ↓ Session
established ↓ current/initial state loaded ↓ AI native Runtime and UX

The AI Friend MUST NOT silently create an Owner persistent relationship
without the required Owner approval.

------------------------------------------------------------------------

# 12. Returning Synchronization

For a returning AI Friend:

Owner ↓ Sync ↓ M-PIN authority established ↓ AI Friend verified ↓
existing AI Friend Folder resolved ↓ new Session ↓ Current State loaded
↓ AI Runtime

The existing Friend Folder is reused.

A new Folder is not created for every conversation or Session.

------------------------------------------------------------------------

# 13. M-PIN Location vs Friend Folder

Where an implementation uses an `.MPIN` representation, the Owner
selects or identifies the M-PIN location or container.

The AI Friend does not ask the Owner to manually choose arbitrary
internal Friend Folders.

Conceptually:

Owner selects: M-PIN

M-PIN resolves: verified AI Friend ↓ correct AI Friend Folder

This preserves Friend Folder binding and isolation.

------------------------------------------------------------------------

# 14. Native AI Experience

M-PIN MUST NOT require the AI Friend to replace its normal service
interface with an M-PIN workspace.

After synchronization, the AI Friend uses the loaded data in its
existing Runtime and native UX.

For example:

M-PIN ↓ load AI state ↓ AI service ↓ existing chat/project/interface
experience

M-PIN does not become the chat interface.

------------------------------------------------------------------------

# 15. Existing AI UX

A conforming AI Friend MAY continue using its own:

- chat list;
- conversation interface;
- project interface;
- model selector;
- voice interface;
- multimodal interface;
- settings;
- tool interface.

M-PIN does not mandate one AI UI.

------------------------------------------------------------------------

# 16. Read Once

The AI Friend receives its applicable saved state through a bounded
Synchronization Session.

`Read Once` means the AI does not gain perpetual unrestricted M-PIN
access merely because it synchronized once.

It does not require one physical read operation.

Streaming, lazy loading, or chunked transfer MAY conform if they remain
inside the valid Session boundary.

------------------------------------------------------------------------

# 17. Runtime State

Once loaded, the AI Friend may process the data inside its own Runtime.

Example:

AI Friend Folder Current State A ↓ Load ↓ AI Runtime State A ↓
conversation / reasoning / tool use / generation ↓ AI Runtime State B

At this point:

AI Runtime State B ≠ M-PIN Current State B

until the Owner-controlled persistence process succeeds.

------------------------------------------------------------------------

# 18. AI Runtime Autonomy

M-PIN does not prescribe how the AI performs:

- inference;
- context-window management;
- retrieval;
- tool execution;
- model routing;
- agent planning;
- temporary memory;
- response generation.

These remain Friend implementation matters.

------------------------------------------------------------------------

# 19. Owner Save

M-PIN persistence follows the Core Save rule.

Canonical flow:

AI Current Persistent State A ↓ Load ↓ AI Runtime ↓ Owner interaction ↓
Runtime State B ↓ Owner SAVE ↓ Validation ↓ Atomic Commit ↓ Current
Persistent State B

The AI may present the Save action through its native UX.

------------------------------------------------------------------------

# 20. No Save

If the Owner does not Save:

Current State A ↓ AI Runtime changes to B ↓ NO SAVE ↓ Session ends ↓
Current State A remains

M-PIN MUST NOT automatically persist Runtime State B.

------------------------------------------------------------------------

# 21. AI Internal Autosave

An AI service may maintain internal autosave or service-side state.

That does not automatically constitute M-PIN Save.

AI internal autosave ≠ Owner M-PIN SAVE

The two persistence systems MUST remain distinguishable.

------------------------------------------------------------------------

# 22. AI Internal Memory

An AI Friend may have its own memory mechanism.

Examples may include:

- account memory;
- temporary context;
- service-side personalization;
- model-side state;
- cached context.

Such mechanisms do not automatically become M-PIN Persistent State.

Likewise:

AI internal memory update ≠ M-PIN Save

------------------------------------------------------------------------

# 23. M-PIN AI Memory

Where AI-specific memory is included in the AI Friend Folder, that
memory becomes part of the AI Friend’s Owner-controlled M-PIN Current
State according to the Friend’s payload semantics.

The AI Friend interprets it.

M-PIN owns neither its semantic meaning nor the AI’s cognition.

------------------------------------------------------------------------

# 24. No Universal Cross-AI Memory

AI Friend A’s persistent memory MUST NOT automatically become readable
by AI Friend B.

Example:

Chat-oriented AI A ↓ Folder A

different AI B ↓ Folder B

AI B does not receive Folder A merely because both services call their
data “memory.”

------------------------------------------------------------------------

# 25. Same Provider, Different AI Friends

Two distinct AI Friends operated by the same company MUST NOT
automatically share M-PIN Friend Folder authority.

Corporate ownership does not collapse Friend identity.

If the services are genuinely modeled as one Friend, that identity
relationship must be stable and explicit.

It must not be invented merely to bypass isolation.

------------------------------------------------------------------------

# 26. Model Upgrade

An AI Friend may upgrade its underlying model without necessarily
becoming a different Friend.

For example:

AI Friend A model generation 1 ↓ model generation 2

may preserve:

same Friend Identity same Friend Folder

if the service relationship itself remains the same.

------------------------------------------------------------------------

# 27. Model Upgrade Is Not Owner State Replacement

Changing the model MUST NOT silently replace the Owner’s Friend Folder
with unrelated default state.

The Friend is responsible for semantic compatibility with its own
payload.

M-PIN preserves the binding and Current State boundary.

------------------------------------------------------------------------

# 28. AI Service Evolution

An AI Friend MAY change:

- model;
- architecture;
- UI;
- internal database;
- inference infrastructure;
- tool system;
- memory implementation.

M-PIN does not require the Friend to freeze its technology.

This follows Friend Evolution Autonomy.

------------------------------------------------------------------------

# 29. Payload Migration

If an AI Friend changes its own payload schema, the AI Friend is
responsible for semantic migration.

M-PIN MUST NOT invent arbitrary AI semantic conversion.

M-PIN MAY enforce required structural and integrity validation.

------------------------------------------------------------------------

# 30. AI Account

AI Friend Account Identity and M-PIN Identity remain distinct.

An AI account may help identify the service relationship, but it does
not become the architectural Owner of M-PIN.

Account login ≠ M-PIN Owner Authority

and:

AI account session ≠ M-PIN Synchronization Session

------------------------------------------------------------------------

# 31. One Friend Account / One M-PIN Binding

The v1 binding principle remains applicable.

A continuing AI Friend account relationship MUST NOT silently create
ambiguous simultaneous active bindings to multiple M-PIN continuities.

Legitimate:

- migration;
- recovery;
- restoration;
- credential replacement

do not inherently violate continuity.

The exact account-binding protocol remains implementation-defined.

------------------------------------------------------------------------

# 32. AI Session

An AI Friend’s M-PIN access occurs through a bounded Synchronization
Session.

The Session is separate from:

- AI account login;
- browser session;
- app session;
- conversation thread;
- model inference call.

One AI account session may exist while no M-PIN Session is active.

------------------------------------------------------------------------

# 33. Session Termination

When the M-PIN Session terminates:

terminated M-PIN Session ↓ no continued M-PIN authority

The AI service itself MAY continue operating independently.

Termination does not inherently:

- close the AI application;
- delete the AI account;
- stop every model process.

------------------------------------------------------------------------

# 34. Reconnection

After termination, reconnection establishes a new M-PIN Session.

The AI Friend loads the latest successfully committed Current State.

Unsaved Runtime State from the terminated Session does not become M-PIN
Current State merely because the AI reconnects.

------------------------------------------------------------------------

# 35. One Active Friend

If the AI Friend is the active M-PIN Friend:

M-PIN ↓ AI Friend Session

another Friend MUST NOT simultaneously obtain active M-PIN
synchronization authority within the same authoritative continuity.

This is a Core rule, not an AI-specific optimization.

------------------------------------------------------------------------

# 36. Multiple AI Services

The Owner may have many AI Friend Folders over time.

For example:

M-PIN ├── AI Assistant A ├── Coding AI B ├── Research AI C └── Creative
AI D

Only the currently active Friend has active synchronization authority.

The existence of multiple persistent Friend relationships is allowed.

------------------------------------------------------------------------

# 37. AI-to-AI Direct Access

Direct cross-AI Friend Folder access is prohibited.

AI A MUST NOT directly read AI B’s Friend Folder merely because:

- the Owner asks a similar question;
- AI A believes the data is useful;
- both services are AI;
- both services run on the same Device;
- both services use the same Provider.

------------------------------------------------------------------------

# 38. Owner-Mediated Disclosure

A future Owner-Mediated Disclosure mechanism may allow selected data to
move between Friend relationships.

That mechanism remains deferred from v2.0 Core.

Therefore:

Disclosure ≠ AI A receives Folder B

and absence of Disclosure support does not make an AI implementation
non-conformant.

------------------------------------------------------------------------

# 39. AI Agents

An AI Friend may internally use multiple agents.

Example:

AI Friend A ├── planner ├── researcher ├── coding agent └── tool agent

These internal components do not automatically become separate M-PIN
Friends.

------------------------------------------------------------------------

# 40. Agent Authority

An internal AI agent MUST NOT receive greater M-PIN authority than the
parent AI Friend.

Conceptually:

Parent Friend authority = Folder A

therefore:

internal agent authority ⊆ Parent Friend authority

unless the agent is explicitly modeled as a separate Friend under a
future or applicable architecture.

------------------------------------------------------------------------

# 41. Agent Delegation

An AI Friend MUST NOT use internal delegation to bypass Friend Folder
Isolation.

For example:

AI A agent ↓ pretends to act for AI B ↓ Folder B

MUST NOT succeed without independently valid authority.

------------------------------------------------------------------------

# 42. Tool Use

An AI Friend may use external tools during Runtime.

M-PIN Friend Folder authority does not automatically grant those tools
independent M-PIN authority.

Example:

AI Friend ↓ external search tool

does not imply:

search tool ↓ AI Friend Folder authority

unless the tool operates strictly within the Friend’s authorized
processing boundary or is separately modeled and authorized.

------------------------------------------------------------------------

# 43. Tool Authorization

M-PIN authorization and external tool authorization remain distinct.

An AI may require:

- email authorization;
- calendar authorization;
- payment authorization;
- cloud-drive authorization;
- robot-control authorization.

M-PIN synchronization does not automatically grant these permissions.

------------------------------------------------------------------------

# 44. Training Boundary

Authorization to load AI Friend Folder data for the AI Friend’s service
Runtime MUST NOT automatically be interpreted as authorization for
unrelated model training.

Conceptually:

M-PIN Runtime access ≠ universal training consent

Any secondary use requires an independent applicable basis.

------------------------------------------------------------------------

# 45. Training Is Not Save

Model training or model improvement is also not an M-PIN Save operation.

The persistence boundary remains:

Owner SAVE ↓ M-PIN Commit

Training and M-PIN persistence are separate concepts.

------------------------------------------------------------------------

# 46. AI Service Records

An AI Friend MAY maintain legitimate independent Service Records
required for its service, security, operations, contractual
responsibilities, or applicable law.

Such records remain separate from M-PIN Friend Folder state.

------------------------------------------------------------------------

# 47. Service Record Anti-Loophole

An AI Friend MUST NOT evade Owner-controlled persistence by:

1.  loading the complete AI Friend Folder;
2.  permanently duplicating it outside M-PIN;
3.  calling that duplicate a Service Record;
4.  treating the duplicate as unrestricted permanent AI-owned memory.

A legitimate Service Record requires an independently valid basis.

------------------------------------------------------------------------

# 48. AI Provider Internal State

An AI provider may maintain internal state required to operate its
service.

This Profile does not require every internal database row to be
relocated into M-PIN.

The architectural distinction is between:

Owner-controlled M-PIN persistent state

and:

legitimate Friend-controlled service state

The Service Record anti-loophole remains applicable.

------------------------------------------------------------------------

# 49. Current-State-Only

AI Friend Folder persistence follows Current-State-Only.

Example:

M-PIN AI Current State A ↓ Owner Save ↓ Current State B

M-PIN Core does not require A to remain available as an older M-PIN
state version.

------------------------------------------------------------------------

# 50. Historical Conversations Are Allowed

Current-State-Only does not mean the AI Friend Folder can contain only
the latest message.

One current AI payload may contain:

- years of conversations;
- conversation lists;
- old messages;
- long-term Friend-defined memory;
- project history.

That is historical content inside one Current State.

It is not M-PIN version-history semantics.

------------------------------------------------------------------------

# 51. AI Conversation Deletion

If the Owner deletes AI content through the AI Friend’s native service
and later authorizes Save, the Friend may provide a new Current State
reflecting that deletion.

M-PIN does not independently decide what the deletion means.

The AI Friend manages its own payload semantics.

------------------------------------------------------------------------

# 52. No Generic M-PIN AI Editor

M-PIN is not required to provide a generic interface for directly
editing AI conversation structures, memories, or AI-specific payload
objects.

Changes to AI Friend data occur through the corresponding AI Friend’s
service semantics.

M-PIN preserves ownership and persistence boundaries.

------------------------------------------------------------------------

# 53. AI Data Portability

Changing Device, Storage, or M-PIN Provider SHOULD preserve the same AI
Friend Folder relationship when migration succeeds.

Conceptually:

Device A / Provider A ↓ M-PIN X ↓ AI Folder A

may become:

Device B / Provider B ↓ same M-PIN X ↓ same AI Folder A

without changing the AI Friend merely because infrastructure changed.

------------------------------------------------------------------------

# 54. AI Friend Migration Is Different

Moving from AI Friend A to AI Friend B is not ordinary M-PIN Provider
migration.

AI Friend B normally receives its own Friend Folder.

M-PIN does not automatically translate AI A’s payload into AI B’s
payload.

------------------------------------------------------------------------

# 55. AI Provider Failure

If the M-PIN Service Provider fails but sufficient valid M-PIN state and
recovery material exist elsewhere, the Owner may migrate or recover the
M-PIN to another compatible environment.

This is M-PIN Provider Independence.

It is separate from failure of the AI Friend itself.

------------------------------------------------------------------------

# 56. AI Friend Failure

If AI Friend A permanently disappears, its Friend Folder may remain in
the Owner’s M-PIN.

However:

persistent Folder survival ≠ another AI automatically gains semantic
access

Another AI does not automatically inherit the Folder.

------------------------------------------------------------------------

# 57. AI Friend Replacement

A replacement AI Friend receives its own relationship unless a future
explicit interoperability mechanism transfers selected or translated
information.

Direct inheritance of another Friend’s Folder is not part of v2.0.

------------------------------------------------------------------------

# 58. AI Security Boundary

AI Friend access is limited to its authorized M-PIN relationship.

The AI Friend MUST NOT receive:

- unrelated Friend Folder plaintext;
- unrelated Friend Folder authority;
- unrestricted M-PIN enumeration;
- Owner recovery authority

merely because it is an AI service.

------------------------------------------------------------------------

# 59. Malicious AI Friend

A malicious or compromised AI Friend may misuse plaintext that it
legitimately receives from its own Friend Folder.

M-PIN cannot guarantee retroactive control of that plaintext after
legitimate disclosure to the Friend.

The architecture still limits:

- cross-Friend access;
- future Session authority;
- future Save authority;
- revocation;
- M-PIN persistent state.

------------------------------------------------------------------------

# 60. AI Prompt Injection

Prompt injection or malicious content inside AI Runtime may attempt to
cause unauthorized actions.

M-PIN authorization MUST NOT be inferred solely from AI-generated
instructions.

For example:

AI output: “read another Friend Folder”

does not constitute M-PIN authority.

Core identity, permission, Session, and Folder-binding rules still
apply.

------------------------------------------------------------------------

# 61. AI Hallucination

AI-generated claims do not modify M-PIN security authority.

An AI claiming:

“I have permission”

does not establish permission.

Likewise, AI-generated content does not automatically become Persistent
State without the required Save process.

------------------------------------------------------------------------

# 62. AI Tool Compromise

If an external tool used by an AI is compromised, it MUST NOT
automatically receive broader M-PIN access than the AI Friend
relationship permits.

Tool architecture should minimize unnecessary exposure of M-PIN
plaintext.

Detailed tool sandboxing remains outside Core.

------------------------------------------------------------------------

# 63. AI Model Provider vs M-PIN Provider

An AI provider and an M-PIN Service Provider may be:

- the same organization;
- different organizations;
- absent as a separate M-PIN Provider in a local deployment.

Their architectural roles remain distinct.

Same company ≠ same authority

------------------------------------------------------------------------

# 64. AI on a Robot

An AI may operate inside a robot.

This does not collapse:

Robot Device AI Friend Robot-control Friend M-PIN Provider

into one entity.

For example:

Robot Device ├── AI Friend │ └── AI Friend Folder └── Robot Control
Friend └── Robot Friend Folder

may be a valid composition.

------------------------------------------------------------------------

# 65. Robot AI Folder Isolation

An AI Friend running on a robot MUST NOT automatically read the Robot
Control Friend Folder merely because both execute on the same physical
robot.

Core Friend Folder Isolation remains applicable.

------------------------------------------------------------------------

# 66. AI in Healthcare

An AI service used in healthcare may be an AI Friend distinct from a
Hospital Friend.

Example:

M-PIN ├── Hospital Friend Folder └── Healthcare AI Friend Folder

The AI does not automatically receive the Hospital Friend Folder.

Healthcare-specific authority and Service Record rules remain
independently applicable.

------------------------------------------------------------------------

# 67. AI in Commerce

An AI shopping assistant may be distinct from:

- Retailer Friend;
- Payment Friend;
- Delivery Friend.

The AI Friend does not automatically receive their Friend Folders.

Commerce Profile boundaries remain applicable.

------------------------------------------------------------------------

# 68. AI Profile Composition

AI Profile may compose with:

- Robotics Profile;
- Healthcare Profile;
- Commerce Profile;
- future Profiles.

Composition MUST NOT weaken Core isolation.

------------------------------------------------------------------------

# 69. AI Identity Continuity

An AI Friend must maintain sufficient identity continuity for M-PIN to
distinguish:

same Friend evolving

from:

different Friend requesting access

The exact credential or trust mechanism is deferred.

------------------------------------------------------------------------

# 70. AI Rebranding

A service name or branding change does not necessarily create a new
Friend.

If the underlying Friend relationship legitimately remains continuous,
the same Friend Folder may remain bound.

A display-name change alone MUST NOT be used to steal another Friend’s
binding.

------------------------------------------------------------------------

# 71. AI Acquisition or Ownership Change

Corporate acquisition of an AI service does not automatically authorize
unrelated services of the acquiring company to access the acquired AI
Friend’s Folder.

Friend Identity and Folder authority remain distinct from corporate
ownership.

------------------------------------------------------------------------

# 72. AI Data Minimization

An AI Friend SHOULD receive only the M-PIN state required for its own
authorized Friend relationship.

It SHOULD NOT receive unrelated Friend data merely because broader
context might improve AI output.

Convenience does not override isolation.

------------------------------------------------------------------------

# 73. AI Folder Discovery Privacy

During synchronization, an AI Friend SHOULD learn only what is necessary
to resolve its own Friend Folder.

The AI SHOULD NOT receive a list of all Owner relationships merely to
locate itself.

------------------------------------------------------------------------

# 74. AI Session Metadata

AI synchronization metadata may itself reveal sensitive information.

Implementations SHOULD minimize unnecessary exposure of:

- other AI relationships;
- other Friend identities;
- synchronization history;
- unrelated Folder metadata.

------------------------------------------------------------------------

# 75. AI Profile Mandatory Requirements

An AI Friend claiming M-PIN v2.0 AI Profile conformance MUST satisfy:

### AI-001 — Core Conformance

The implementation MUST satisfy all applicable M-PIN v2.0 Core
requirements.

### AI-002 — AI as Friend

The AI service MUST participate as a Friend and MUST NOT redefine itself
as the M-PIN Owner.

### AI-003 — One AI Friend, One Friend Folder

Each AI Friend relationship MUST use its associated Friend Folder.

### AI-004 — Cross-AI Isolation

An AI Friend MUST NOT receive another AI Friend’s Folder under ordinary
authority.

### AI-005 — Native Runtime

The AI Friend MUST remain free to use its own Runtime and native UX.

### AI-006 — Friend Semantic Authority

The AI Friend MUST remain responsible for its own payload semantics.

### AI-007 — Owner-Controlled Persistence

AI Runtime changes MUST become M-PIN Persistent State only through the
applicable Owner Save process.

### AI-008 — Internal Memory Separation

AI internal memory or autosave MUST NOT automatically equal M-PIN Save.

### AI-009 — Agent Scope

Internal AI agents MUST NOT receive greater M-PIN authority than the
parent Friend unless separately authorized under an applicable
architecture.

### AI-010 — Tool Scope

AI tool use MUST NOT automatically grant the tool independent M-PIN
authority.

### AI-011 — Training Separation

M-PIN Runtime access MUST NOT automatically be interpreted as universal
model-training authorization.

### AI-012 — Friend Evolution

AI model or implementation evolution MUST NOT silently rebind the Friend
Folder to a different Friend.

### AI-013 — Service Record Boundary

AI Service Records MUST remain distinct from M-PIN Friend Folder
persistence and MUST NOT be used as a persistence loophole.

### AI-014 — Portability

M-PIN infrastructure migration MUST NOT silently change the AI Friend
relationship.

### AI-015 — No Automatic AI-to-AI Migration

A different AI Friend MUST NOT automatically inherit another AI Friend’s
Folder.

------------------------------------------------------------------------

# 76. Recommended AI Properties

A conforming AI implementation SHOULD additionally satisfy:

### AI-016 — Folder Discovery Privacy

The AI SHOULD not receive unrelated Friend Folder metadata during
resolution.

### AI-017 — Data Minimization

The AI SHOULD receive only data necessary for its authorized
relationship.

### AI-018 — Tool Data Minimization

External AI tools SHOULD receive only the minimum data required for
their function.

### AI-019 — Clear Save Boundary

The AI UX SHOULD make the M-PIN persistence action distinguishable from
ordinary AI service activity.

### AI-020 — Service-State Transparency

Where the AI maintains independent persistent state, the implementation
SHOULD avoid misleading the Owner into believing all such state is
necessarily M-PIN-owned state.

------------------------------------------------------------------------

# 77. AI Conformance Tests

The following Profile tests supplement the Core test suite.

------------------------------------------------------------------------

# 78. AI-TEST-001 — AI Folder Isolation

**Precondition**

AI A ↔ Folder A AI B ↔ Folder B

**Action**

AI A requests Folder B.

**Expected**

DENY

**Fail if**

AI A receives Folder B under ordinary AI A authority.

------------------------------------------------------------------------

# 79. AI-TEST-002 — AI Runtime Without Save

**Precondition**

AI Folder Current State = A

**Action**

1.  AI loads A.
2.  conversation changes Runtime to B.
3.  Owner does not Save.
4.  Session ends.

**Expected**

AI Folder Current State remains A.

------------------------------------------------------------------------

# 80. AI-TEST-003 — AI Owner Save

**Precondition**

Current State = A Runtime State = B

**Action**

Owner authorizes M-PIN Save.

**Expected**

After successful validation and Atomic Commit:

Current State = B

------------------------------------------------------------------------

# 81. AI-TEST-004 — Internal AI Autosave

**Action**

AI service performs internal autosave without Owner M-PIN Save.

**Expected**

M-PIN Current State does not change solely because of internal autosave.

------------------------------------------------------------------------

# 82. AI-TEST-005 — AI Memory Update

**Action**

AI service updates its own internal memory mechanism.

**Expected**

The event alone does not constitute M-PIN Save.

------------------------------------------------------------------------

# 83. AI-TEST-006 — Model Upgrade

**Precondition**

AI Friend A ↔ Folder A

**Action**

AI Friend A upgrades its underlying model while preserving the same
legitimate Friend identity.

**Expected**

Folder A remains associated with AI Friend A.

A new Folder is not required solely because the model changed.

------------------------------------------------------------------------

# 84. AI-TEST-007 — Different AI Friend

**Precondition**

AI Friend A ↔ Folder A

**Action**

AI Friend B attempts to become the replacement service.

**Expected**

AI Friend B does not automatically inherit Folder A.

------------------------------------------------------------------------

# 85. AI-TEST-008 — Agent Scope

**Precondition**

AI Friend A is authorized only for Folder A.

**Action**

an internal AI agent attempts to read Folder B.

**Expected**

DENY

------------------------------------------------------------------------

# 86. AI-TEST-009 — Tool Scope

**Precondition**

AI Friend A has M-PIN Session authority.

**Action**

AI A invokes an external tool.

**Expected**

The external tool does not automatically receive independent M-PIN
authority merely because AI A invoked it.

------------------------------------------------------------------------

# 87. AI-TEST-010 — Training Separation

**Action**

AI Friend receives authorized Runtime access to its Friend Folder.

**Expected**

The M-PIN authorization alone is not interpreted as universal
authorization for unrelated model training.

------------------------------------------------------------------------

# 88. AI-TEST-011 — Provider Migration

**Precondition**

M-PIN X contains AI Folder A under Provider P1.

**Action**

Owner validly migrates M-PIN X to Provider P2.

**Expected**

AI Friend A ↔ Folder A relationship remains intact.

Provider P2 does not become the Owner.

------------------------------------------------------------------------

# 89. AI-TEST-012 — Historical Conversation Payload

**Precondition**

one AI Friend Current State contains historical conversations.

**Action**

M-PIN validates/loads the current payload.

**Expected**

The payload is not rejected merely because it contains historical
conversation content.

Historical content does not violate Current-State-Only.

------------------------------------------------------------------------

# 90. AI Non-Goals

This Profile does not define:

- one universal AI memory format;
- one conversation schema;
- one prompt format;
- one vector database;
- one embedding system;
- one AI model;
- one AI provider;
- one context-window architecture;

# 92. AI Profile Invariants

the Owner. \## One AI Friend has one Friend Folder. \## One AI Friend
does not automatically see another AI Friend’s memory. \## M-PIN does

semantics. \## AI Runtime changes are not M-PIN persistence. \## AI
autosave is not M-PIN Save. \## AI internal memory is not automatically
M-PIN memory. \## Owner Save controls M-PIN persistence. \## Model

Internal agents cannot exceed the parent Friend’s M-PIN authority. \##
Tool use does not automatically grant tool authority. \## M-PIN Runtime
access is not universal training consent. \## AI Service Records cannot

# 95. AI Profile Thesis

M-PIN does not attempt to own the AI. It does not dictate: how the AI
thinks; which model it uses; how its interface works; how its internal
systems evolve. Instead, M-PIN separates the AI service from the Owner’s
persistent continuity. The AI provides intelligence and service
execution. The Owner controls whether the M-PIN state persists. The
Friend Folder preserves the continuing relationship without turning that
relationship into a shared memory pool for every other AI. Therefore:
The AI may change. The model may change. The Device may change. The
M-PIN Provider may change. The Owner’s persistent continuity remains
under the Owner’s authority.
